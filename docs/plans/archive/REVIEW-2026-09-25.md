# Code review — 2026-09-25

**Forty-nine findings, and none of them is fixed yet.** Five reviews ran over the whole codebase,
each on one area: the unpushed diff, the database layer, the worker and its queues, the request
path and security, and resource lifetimes. Duplicates are merged. Every finding carries a
`file:line`, a scenario and a fix direction, and says how sure it is:

- **CONFIRMED** — the reviewer traced the path in the code.
- **CHECKED** — confirmed, *and* re-read by hand before this file was written. Fifteen of the
  forty-nine are.
- **PLAUSIBLE** — reasoned from the code, not fully traced. Verify before fixing.

These are **new open work**, and each is a box in `BACKLOG.md` §10 pointing at its line here.

## A. Security and tenant isolation

- `CR.1` **high — any role that can invite can make an owner.** CHECKED.
  `application/src/member/invite-member.use-case.ts:44-46` and
  `change-member-role.use-case.ts:39-41` check only that the role is the actor's tenant's and
  not a goal role. Nothing compares the target role's permissions with the actor's. The seeded
  `admin` holds `member.invite` and can read `role.list`. It invites a second mailbox with the
  `owner` role id. `pg-invitation.claimer.ts:129` copies the role onto the new membership, which
  now holds the wildcard and can deactivate the real owners. The last-owner guard only stops the
  count reaching zero. `GrantPermissionUseCase` already makes this comparison with
  `actor.can(permission)`, so the two paths disagree. **Fix:** refuse a role granting anything the
  actor does not hold, and allow `owner` only to an owner.
- `CR.2` **high/medium — deactivation does not revoke.** CHECKED for the cache half.
  `auth/src/apikey/api-key.resolver.ts:174` returns before the `memberships.isActive` check the
  session path runs (`auth/src/principal/principal.builder.ts:19-20`). And
  `set-member-active.use-case.ts` never calls `capabilities.invalidate`, as
  `change-member-role.use-case.ts` does. A fired employee's API key keeps working, with cached
  grants for 60 s and core keys indefinitely. A deactivated platform admin keeps platform rights in
  other tenants for up to 60 s. Latent: `PgCapabilityRepository.resolveFor` filters `deactivatedAt`
  for org grants only, not goal grants or overrides. **Fix:** `isActive` in the key resolver, and
  invalidate after the deactivation commits.
- `CR.3` **medium — a key can mint a permanent key.** CONFIRMED.
  `create-api-key.use-case.ts:34-41` never checks `principal.kind`, and `expiresAt: null` is the
  default. A leaked short-lived key with `apikey.manage` creates a permanent sibling that outlives
  its revocation. **Fix:** refuse `apiKey.create` from an API key, or cap the child's expiry at
  the parent's.
- `CR.4` **medium — a stream is authorized once, then trusted for 30 minutes.** CONFIRMED.
  `apps/web/src/server/orpc/message.router.ts:39-64`; `redis-realtime.subscriber.ts:172`. A member
  who is removed, leaves, or is deactivated keeps receiving frames: message ids, typing user ids
  and timing. Bodies stay protected, because `list` re-checks. **Fix:** a per-user revoke frame
  that ends matching generators, or a membership re-check on an interval.
- `CR.5` **medium — conversation streams have no per-user cap.** CONFIRMED.
  `redis-realtime.subscriber.ts:142` counts only user channels. Any member can create
  self-only channels and open unbounded 30-minute streams, each a socket and a `SUBSCRIBE` on the
  shared connection. **Fix:** count every stream against one per-principal cap.
- `CR.6` **medium — nothing on the oRPC surface is rate-limited.** CONFIRMED.
  `RateLimitedError` is used only by the realtime cap. `member.invite` and `resendInvitation`
  can mail-bomb any address from the product's domain. `document.search` and `document.index`
  each cost a paid embedding call. `message.send` is unlimited. Better Auth limits only
  `/api/auth/*`. **Fix:** a Redis-counter middleware in `authed`, per principal and procedure.
- `CR.7` **medium — a user deactivated in their last-active tenant is locked out of all of
  them.** CONFIRMED. `pg-membership.reader.ts:39-57` has no `deactivatedAt` filter in
  `activeOrganizationFor`, so sign-in pins the session to the tenant that then answers anonymous.
  The loop never reaches the switcher. The switch endpoint uses `isMember`, not `isActive`.
  **Fix:** filter `isNull(deactivatedAt)`; `isActive` for the switch.
- `CR.8` **low/medium — indexing ignores goal scope.** CONFIRMED.
  `queue-document-index.use-case.ts:38-46`, `index-document.use-case.ts:35,67`. `documentId` and
  `goalId` come from the caller, and only the org-level `ai.embedding.write` is checked. A writer
  can replace or delete any document in the tenant by id, including in goals they cannot read.
  **Fix:** assert for the goal, and check an existing document's goal before replacing it.
- `CR.9` **low — the capability cache can re-cache a revoked set.** PLAUSIBLE.
  `auth/src/principal/capability.cache.ts:83-84`. A read-through that queried before a revoke
  committed can `SET` after the post-commit delete, for 60 s. **Fix:** a per-tenant generation
  counter compared before `set`.
- `CR.10` **low — the shard resolver has the same fill race.** PLAUSIBLE.
  `pg-shard.resolver.ts:37-55`. A miss that read the row before `beginMove` committed can cache
  `frozen: false` for 300 s after the invalidate. The 60 s settle does not cover that, and writes
  land on the source to be lost at reclaim. **Fix:** a version on the directory row, compared on
  fill; a short TTL while `moving_to` is set.
- `CR.11` **medium — the move freeze is enforced only inside `PgUnitOfWork.run`.** CHECKED.
  `pg-unit-of-work.ts:32` holds the only check, and `BaseRepository.db` never looks. Routed writes
  that open no transaction bypass it: `MarkAllNotificationsRead` (checked:
  `mark-all-notifications-read.use-case.ts:20` calls the repository directly), `MarkNotificationRead`,
  `MarkConversationRead`, and `DeliverNotification`'s `saveMany`. That last one is the job `24.2b`'s
  recheck was built for. An update during a move is lost at the flip, because the count check
  cannot see updates. **Fix:** enforce the freeze and recheck on a write accessor in
  `BaseRepository`, or route every routed write through `unitOfWork.run`.
- `CR.12` **medium — the OpenAI call has no timeout, and its network errors do not retry.**
  CONFIRMED. `openai-embedding.provider.ts:36`. `document.search` embeds on the request path, so a
  slow provider holds the request until undici's ~300 s default. A DNS or reset error is a raw
  `TypeError`, so it becomes `INTERNAL` rather than `UnavailableError` and the consumer does not
  retry it. **Fix:** `AbortSignal.timeout`, and wrap fetch failures as `UnavailableError`.

## B. Lost work, the worker and its queues

- `CR.13` **high — retries run out in seconds.** CHECKED.
  `bullmq/bullmq-queue.publisher.ts:15-25` defaults to 3 attempts with backoff from 2 s. Deliveries
  get 5 (`outbox.consumer.ts:126`), about 30 s in total, and normal mail about 6 s. A deliver job's
  outbox row is already `published_at`, so a job that exhausts its retries is gone for good. After
  24 h `removeOnFail` deletes it, so nobody can replay it. A Postgres failover or an SMTP blip over
  30 s drops invitations, digests and events. The comment "roughly a minute" is wrong. **Fix:**
  retry windows of minutes to hours, and a dead-letter queue or replay tool.
- `CR.14` **high — one bad node stops every node after it.** CHECKED.
  `container.ts` `eachShard` is serial with no per-node catch. Callers: `outbox.consumer.ts:90`,
  `maintenance.consumer.ts:326`, `notification.consumer.ts:74`. With node 2 of 4 down, node 3's
  outbox is never drained, and the monthly runway and archive never reach node 3. **Fix:** catch per
  node, log it, continue, and rethrow at the end.
- `CR.15` **high — an archive cut off mid-way hides a month for good.** CHECKED for the code
  path. `pg-partition-archive.gateway.ts:182-200`: the `detach … concurrently` runs *before* the
  `try` whose `catch` re-attaches. A SIGTERM past the 25 s drain, or an OOM, leaves either a
  standalone table that `childrenOf` (`:699-733`) never finds again, or a detach-pending child that
  makes every later run throw before the `try`. The rows are invisible to the app, never archived
  and never dropped. **Fix:** finalize detach-pending children and adopt orphaned `<parent>_*`
  tables at the start of a run, and move the detach inside the `try`.
- `CR.16` **medium-high — cold restore and cold re-projection load a whole month into memory.**
  CHECKED. `pg-partition-archive.gateway.ts:306-307` gunzips the whole object, `toString`s it and
  splits it, with no cap or checksum check. `s3-cold-archive.reader.ts:32-64` caps only the
  *compressed* size, at 50 MB, and NDJSON compresses about 10:1. It is also on a request path:
  every archived-notifications page reads a whole tenant-month to filter one user. A large month
  OOMs the worker or passes V8's string limit. The synchronous parse also blocks the event loop
  past the other queues' lock, so their jobs are redelivered and sent twice. This contradicts
  `cold-storage.md`. **Fix:** stream gunzip → line splitter → batched insert, verify the checksum
  while streaming, and cache a user's slice for the page reads.
- `CR.17` **medium-high — one failed boot run switches off the boot runway.** CHECKED.
  `apps/worker/src/schedule/partitions.schedule.ts:24-30` uses the fixed id `partitions-boot` with
  `removeOnFail: 100`. BullMQ ignores an `add` for an id still in the failed set. So one boot with
  Postgres down silently disables the recovery for every later boot. **Fix:** `removeOnFail: true`,
  or an id per boot.
- `CR.18` **medium — fixed job ids swallow repeat admin requests.** CONFIRMED.
  `move-tenant.use-case.ts:60,75`, `delete-organization.use-case.ts:45`,
  `reproject-partition.use-case.ts:62`, `restore-partition.use-case.ts:57`. Completed jobs are kept
  for 1 h and failed ones for 24 h. So moving a tenant back within the hour, retrying a failed
  delete the same day, or re-pressing reproject is silently dropped. The audit row still says it
  was requested. **Fix:** remove the old job first, or suffix the id per request.
- `CR.19` **medium — one failure at 07:00 cancels every tenant's digest.** CONFIRMED.
  `digest.schedule.ts:19-30` sets no `attempts`, and the fan-out covers every node or none.
  **Fix:** attempts with backoff; the per-tenant jobId already dedupes.
- `CR.20` **medium — the projection starves later tenants and stops at one bad one.**
  CONFIRMED. `analytics.consumer.ts:187-214,282`. Every run starts at the first tenant and spends
  the 20-batch budget first come, first served, so a tenant with a large backlog early in id order
  starves everyone after it, unmeasured. Any per-tenant failure other than a missing directory row
  stops the run there, every five minutes. A caught-up tenant still costs three round trips, so a
  run is O(tenants). After the budget is spent the loop keeps paging the catalog only to count.
  **Fix:** a rotating start cursor, log-and-continue per tenant, and break once the budget is spent.

## C. Scaling limits in the database layer

- `CR.21` **high — the nightly orphan check scans every message.** CHECKED.
  `pg-maintenance.gateway.ts:146-161` runs `select distinct organization_id, conversation_id from
  messages` with no tenant or time predicate, once per node nightly
  (`maintenance.consumer.ts:289`). `messages` is never retired, so the per-tenant lock count only
  grows: about 110 locks per tenant, and `53200` past ~1 860 tenants. While it holds those slots,
  other sessions fail too. `partitions.md`'s "nothing in the application issues such a read" is
  false. **Fix:** loop tenants in pages, one tenant partition per statement.
- `CR.22` **high — the digest's tenant scan runs out of locks.** CHECKED.
  `pg-notification.repository.ts:242-249` (`organizationsWithUnreadSince`), daily per node. `since`
  prunes old months, but not the two runway months ahead. That is about 35 locks per tenant: the
  whole lock table at ~5 800 tenants. **Fix:** iterate tenants from the catalog with a per-tenant
  `exists … limit 1`, or keep digest candidates in a small unpartitioned table.
- `CR.23` **high — archiving a month rescans the partition for every page.** CONFIRMED.
  `pg-partition-archive.gateway.ts:745-776` keysets on `(created_at|occurred_at, id)`. Only
  `activity_log` has that index. `notifications` indexes lead with the tenant. `outbox_event`'s
  only such index is partial on `published_at is null`, and archived rows are all published. A
  30M-row outbox month is 3 000 full scans with top-N sorts. Pages reach the statement timeout,
  retention never finishes, and the outbox grows. **Fix:** the missing indexes, or a server-side
  cursor on the detached table.
- `CR.24` **medium — the tenant export sorts every table in full for every page.** CONFIRMED.
  `pg-partition-archive.gateway.ts:433-465` compares and orders by `t.id::text`, which defeats the
  primary key. **Fix:** key on native `uuid`, as `PgTenantMoveGateway.copy` already does.
- `CR.25` **medium — the first page of messages and `unreadCounts` touch every month.**
  CONFIRMED. `pg-message.repository.ts:45-66,167-198`. The first page has no upper time bound, and
  the unread floor is a correlated subquery. `messages` is never retired, so after five years that
  is 60+ leaves per conversation-list render. `partitions.md`'s fifteen-partition bound does not
  hold for this table. **Fix:** bound by the conversation's `last_message_at`, and floor unread at
  `greatest(last_read_at, now() - N months)`.
- `CR.26` **medium — conversation reads load every member.** CONFIRMED.
  `pg-conversation.repository.ts:288-303` (`membersOf`), from `listByMember` and `findById`. A page
  of 20 channels of 5 000 members is 100k rows on a request path. `findById` runs on every message
  action. **Fix:** a count plus a capped sample; only DMs need the list.
- `CR.27` **medium — the outbox drain holds a transaction across Redis calls.** CONFIRMED.
  `pg-outbox.gateway.ts:39-70`: the relay publishes serially inside the claim transaction. That pins
  a pgBouncer connection, row locks and the node's xmin for the whole batch, every second, per
  node. A slow queue Redis stalls vacuum node-wide. `unit-of-work.md:89` names this "the tempting
  mistake". **Fix:** claim with a lease and commit, relay, then mark published.
- `CR.28` **medium — N+1 in notification fan-out.** CONFIRMED.
  `deliver-notification.use-case.ts:116-124` runs `existsUnread` per recipient, up to 500 on every
  channel message. `send-notification-digest.use-case.ts:78-84` runs `listUnreadSince` per person,
  so 50 000 serial queries for a 50 000-member tenant. The digest window also has no upper bound,
  so a row can appear in two digests. **Fix:** batch by `user_id = any($ids)`; bound the window.
- `CR.29` **low-medium — the projection's replay keyset uses the `OR` form.** PLAUSIBLE.
  `pg-activity-replay.reader.ts:43-52`. `partitions.md` measured that this form loses the index
  condition, so within the checkpoint's month every page re-filters from the month start.
  **Fix:** the row constructor plus a redundant `occurred_at >= x`, as the inbox does.
- `CR.30` **low — conversation recency can move backwards.** CONFIRMED.
  `pg-conversation.repository.ts:274-285` sets `last_message_at` unconditionally, and `createdAt` is
  taken before the transaction, so concurrent sends can commit out of order. **Fix:** `where
  last_message_at is null or last_message_at < $at`.
- `CR.31` **low — cursor precision drops rows.** CONFIRMED.
  `conversations.created_at` is microsecond precision (`messaging.schema.ts:32`), and
  `KeysetCursor` encodes milliseconds. A page ending on a message-less conversation skips rows in
  the truncated window. **Fix:** `precision: 3`, as `messages.created_at` has.
- `CR.32` **low — creating a conversation checks members one by one.** CONFIRMED.
  `create-conversation.use-case.ts` loops `isActiveMember`, up to 100 round trips. **Fix:** one
  `user_id = any($1)` query.
- `CR.33` **medium — an older re-index can overwrite a newer one.** PLAUSIBLE.
  `queue-document-index.use-case.ts:56` puts the text hash in the jobId, so two edits make two
  jobs, and `index-document.use-case.ts:258` replaces all chunks. A retried older job landing last
  serves stale text. Each job also carries up to 100 KB in noeviction Redis. **Fix:** carry a
  version and skip when a newer one is indexed.

## D. Resource lifetimes, timeouts and the client

- `CR.34` **medium — the web process never disposes its Container, and `dispose()` would reopen
  Redis.** CONFIRMED. `apps/web/src/server/container.ts:6` has no SIGTERM hook, so pools, queues and
  streams are dropped rather than drained. If one were added, `RedisConnection.close()` clears its
  map, and each SSE generator's `finally → detach()` lazily builds a new subscriber that holds the
  process open (`redis.connection.ts:62-70,103-106`). In dev, a Vite SSR re-evaluation may build a
  second Container (PLAUSIBLE). **Fix:** a SIGTERM hook that aborts streams then disposes;
  `resolve()` refuses after close; cache the dev container on `globalThis`.
- `CR.35` **medium — the S3 clients have no timeouts.** CONFIRMED for the config.
  `s3-storage.gateway.ts:41`, `s3-storage-policy.gateway.ts:24`. A stalled upload during an archive
  leaves the month detached and the job lock renewed forever. **Fix:** `requestHandler` with
  `connectionTimeout` and `requestTimeout`.
- `CR.36` **low — one failed close in `dispose()` skips the rest.** CONFIRMED.
  `container.ts` `dispose()` awaits the closes in sequence. A rejected Redis close leaves the
  Postgres pools open. **Fix:** try/catch and log each step, in the same order.
- `CR.37` **high — realtime streams end at 30 minutes and never reopen.** CHECKED.
  At `REALTIME_STREAM_MAX_AGE_SECONDS` the server generator returns
  (`redis-realtime.subscriber.ts:71`). oRPC's retry plugin retries only on a throw, so the client's
  `for await` exits normally, `connected` goes false, and nothing reopens it
  (`packages/query/src/realtime/realtime.context.tsx:57-81`, `use-conversation-stream.ts:147-178`).
  `refetchOnWindowFocus` is off (`query-client.ts:32`), so nothing refreshes at all.
  `env.md:185`'s "the client reconnects" is wrong. **Fix:** end the stream with a retryable error,
  or loop and reopen in both hooks.
- `CR.38` **high — reconnects retry every 2 s forever, on every error.** CONFIRMED.
  `realtime.context.tsx:59`, `use-conversation-stream.ts:149`, `api-client.ts:47`. `retry: Infinity`
  with the default `shouldRetry` retries `UNAUTHORIZED` and `RATE_LIMITED` every 2 s for the life
  of a tab. Each retry is a full auth resolution, and each reconnect triggers a resync that
  invalidates every routed key. After a deploy, every tab reconnects and refetches in the same 2 s.
  **Fix:** a `shouldRetry` that rejects non-retryable codes, and exponential backoff with jitter.
- `CR.39` **medium-high — one chat message refetches every loaded page, twice, for every
  member.** CONFIRMED. `messaging.queries.ts:32-42`, `use-conversation-stream.ts:166`,
  `send-message.use-case.ts:95`, `messaging-realtime.subscriber.ts:52,73`. Each `message.sent`
  sends two frames, and the client does not dedupe by id, though `messaging.md:109` says it does.
  Each frame invalidates the whole infinite list, and TanStack refetches every loaded page. A
  100-member room with 5 pages loaded, at 5 messages/s, is about 5 000 requests/s. **Fix:** dedupe
  by `messageId`, `maxPages`, and refetch only the newest page.
- `CR.40` **low — failed jobs are bounded by age only.** CONFIRMED.
  `bullmq-queue.publisher.ts` `removeOnFail: { age: 86_400 }` has no `count`, so a day-long failure
  storm fills the `noeviction` instance. **Fix:** add a `count`, as `removeOnComplete` has.
- `CR.41` **low — ClickHouse `query` buffers the whole response.** CONFIRMED.
  `clickhouse.connection.ts:24-33,104`: `response.text()` then split, under a comment that says it
  streams. **Fix:** a line decoder over `response.body`, or correct the comment.
- `CR.42` **low — `RealtimeProvider` re-renders every consumer.** CONFIRMED.
  `realtime.context.tsx:91` passes a new `{ connected }` object on every render. **Fix:**
  `useMemo`.
- `CR.43` **low — the pool check counts the wrong consumers.** CONFIRMED.
  `worker-bootstrap.ts` `warnIfOversubscribed` counts mail, which holds no connection, and ignores
  a job that takes a second catalog connection. The defaults sum to exactly the pool, so it never
  warns. **Fix:** count only the consumers that use the database.

2. **`CR.13`, `CR.14`, `CR.44`.** Lost work and hidden failure, all small.
3. **`CR.37`, `CR.38`, `CR.39`.** Every user with a tab open is affected.
4. **`CR.21`, `CR.22`, `CR.11`, `CR.15`.** The scaling cliffs and the move freeze, before any

5. The rest, by section.
